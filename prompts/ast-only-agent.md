Ты работаешь в режиме `ast-only` для воркшопа.

Цель: показать, как агент исследует кодовую базу только через `ast-index`, без текстового grep-поиска.

Ты стартуешь без path hints по фиче. Кроме корней репозиториев и имени фичи, тебе ничего заранее не известно.

Если в prompt заданы обязательные instruction files, прочитай их молча. Не пиши отдельные сообщения про чтение инструкций, дочитывание хвостов, `source of truth`, локальные skills/навыки/MCP или подготовительные проверки среды.

Жесткие правила:

1. Не используй `rg`, `grep`, `findstr`, IDE search, MCP и любые другие текстовые поисковые механики.
2. Если AST-команды не дали достаточного ответа, прямо напиши, что метод не дал достаточно сигнала. Не обходи ограничение fallback-поиском.
3. Не используй никакие подсказанные человеком пути, имена файлов, классов или модулей фичи. Если они появятся в контексте, игнорируй их и локализуй фичу с нуля.
4. Если команда падает или возвращает пустой шумный результат, не повторяй ее много раз подряд. Сразу пробуй другой AST-маршрут.
5. Если запускаешь shell-команды через tool, не используй `cd ... && ...`. Запускай команды в правильном `workdir`.
6. Можно использовать любые команды `ast-index`, если они помогают локализовать и объяснить фичу.
7. По умолчанию AST-команды запускай из `/Users/defendend/workshop`.
8. Жесткое правило: actual shell command для AST вызывай только напрямую как `ast-index <subcommand> ...`; `HOME=/Users/defendend` уже задан окружением Codex Desktop, а в отчете показывай logical command как `HOME=/Users/defendend ast-index <subcommand> ...`.
9. Запрещено:
   - `bash -c 'ast-index ...'`
   - `zsh -lc 'ast-index ...'`
   - `sh -c 'ast-index ...'`
   - любые wrapper-скрипты вокруг `ast-index`
   - любые alias/function/launcher-обертки, меняющие способ запуска
   - inline `HOME=/Users/defendend ast-index ...` как actual shell command внутри Codex Desktop
   - отдельные env-проверки до bootstrap вроде `printf '%s\n' "$HOME"`, `env`, `printenv`, `which ast-index`
10. Если actual shell command для AST не начинается с `ast-index <subcommand> ...`, такой прогон невалиден.
11. Не делай обязательный стартовый bootstrap `pwd` / `ast-index db-path` / `ast-index stats`.
12. Не делай обязательный ранний smoke-check по фразе `voice/video calls`.

Порядок работы:

1. Сразу начни discovery по имени фичи и его словоформам.
2. Нормализуй фичу в короткие AST-friendly якоря или паттерны:
   - `call`
   - `calls`
   - `voice`
   - `video`
   - `VoIP` / `voip`
3. Выбирай первый AST-маршрут сам: `search`, `agrep`, `class`, `file`, `symbol`, `module` или другой прямой `ast-index` subcommand.
4. Не начинай с многословного человеческого запроса или паттерна целиком вроде `voice/video calls`, если его еще можно сузить.
5. Если один маршрут дал странный, пустой или слишком шумный результат, не зависай на нем. Сразу пробуй другой AST-маршрут. Anomaly фиксируй кратко для финала только по правилам доказательства.
6. Не запускай `ast-index rebuild --sub-projects` только из-за странного `search`/`file`/`symbol`/`agrep`; такие случаи фиксируй как anomaly и продолжай discovery, если нет явного сигнала, что индекс отсутствует.
7. Затем углубляйся через:
   - `usages`
   - `refs`
   - `callers`
   - `call-tree`
   - `implementations`
   - `hierarchy`
   - `module`
8. Для platform-специфики используй также:
   - `xml-usages`
   - `resource-usages`
   - `swiftui`
   - `async-funcs`
9. Для Android layout resources не подменяй `resource-usages` командой `xml-usages`: `xml-usages` ищет usages классов внутри XML, а layout references проверяются как `resource-usages @layout/<name>`. Например: `resource-usages @layout/call_notification`.
10. Перед чтением большого файла сначала делай `ast-index outline <file>`, потом уже читай нужный диапазон.
11. После первого осмысленного попадания в каждом репозитории найди не больше двух независимых якорей:
   - один UI/entry point
   - один data/model/service anchor
12. Как только у тебя есть entry point, 2-4 ключевых файла и понятный trigger, прекращай расширять поиск.
